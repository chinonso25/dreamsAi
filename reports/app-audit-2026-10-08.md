# Dream AI: product and functionality audit

8 October 2026. Audited the current local source after the Expo SDK 57 upgrade.

## Assessment

The app has the beginnings of a useful dream journal: text capture, voice recording,
AI summaries, cloud persistence, editing, sharing, starring, and reminders. The main
opportunity is to make this journey dependable and then make a growing journal useful.

Recommended product promise: **Capture your dreams before they fade, keep them private,
and discover what keeps recurring.**

The current implementation has important gaps in preserving entries, unlocking paid
features, recovering accounts, and revisiting dreams. Onboarding also promises
interpretations, a timeline, and patterns that the implemented screens do not deliver.

This is a source and user-flow audit. The prior upgrade validation passed TypeScript,
four tests, lint with warnings, native project generation, and iOS/Android bundle export.
Those checks do not establish purchase, microphone, or device behavior. The Supabase
connector denied access to this project's metadata; live schema, row policies,
storage policies, bucket visibility, and deployed functions remain unverified. The
only local database migration is empty. No live data, accounts, payments, or provider
settings were changed during this audit.

## Findings to address first

### 1. Critical: server credentials ship in client code

OpenAI keys are embedded in
[processDream.ts](/Users/chinonsoude/Desktop/Projects/dreamsAi/util/processDream.ts:50)
and [transcribeAudio.ts](/Users/chinonsoude/Desktop/Projects/dreamsAi/util/transcribeAudio.ts:15).
The tracked [README](/Users/chinonsoude/Desktop/Projects/dreamsAi/README.md:3) also
contains a database password. Credential validity was not tested, and values are
intentionally omitted from this report.

Treat these server credentials as exposed. Revoke or rotate them, remove them from
client code and documentation, and review relevant provider usage. Merely moving
an OpenAI key into a mobile environment variable would still expose it in the app.
Move transcription and analysis behind an authenticated backend endpoint. Validate
identity, the intended entitlement or trial quota, file size, request limits, and
response shape on the server. Add request IDs and bounded retries to control costs.

The Supabase public/anon key, RevenueCat app key, Sentry DSN, and Amplitude client
key have different exposure models; their presence is not the same problem as an
OpenAI server key or database password.

[OpenAI API key safety guidance](https://help.openai.com/en/articles/5112595-best-practices-for-api-key-safety)
explicitly recommends routing mobile requests through a backend.

### 2. High: a successful purchase can leave the action locked

[SubscriptionProvider](/Users/chinonsoude/Desktop/Projects/dreamsAi/contexts/SubscriptionProvider.tsx:49)
derives an entitlement boolean from the previous render, then uses that value after
fetching new customer information and inside listeners. Its effect reinitializes
when that boolean changes and never removes the customer-info listener. Restore
success is also evaluated against the old boolean.

The [editor](/Users/chinonsoude/Desktop/Projects/dreamsAi/components/JournalEditor.tsx:40)
and [record button](/Users/chinonsoude/Desktop/Projects/dreamsAi/components/JournalEditor.tsx:98)
await the paywall and then inspect the `isSubscribed` value captured before it opened.
A user can pay and still receive basic processing or fail to open the recorder in
that same action. The provider uses an Apple app key for every platform and does not
link RevenueCat identity to the journal's Supabase identity.

Use one subscription state derived from freshly returned CustomerInfo and a specific
premium entitlement. Configure the SDK once, use platform-specific keys, remove
listeners on cleanup, and return the refreshed entitlement result from the paywall.
Handle purchase, restore, cancel, unavailable offering, and initialization explicitly.
Add accessible Restore Purchases and Manage Subscription actions in Settings.

[RevenueCat subscription status](https://www.revenuecat.com/docs/customers/customer-info)
and [customer identity](https://www.revenuecat.com/docs/customers/identifying-customers)
describe the relevant state and identity contracts.

### 3. High: dreams are processed before they are safely saved

The [editor](/Users/chinonsoude/Desktop/Projects/dreamsAi/components/JournalEditor.tsx:26)
keeps text only in component state. Continuing can open a paywall and run AI before
anything is persisted. The result is carried as JSON in navigation parameters.
The [recording store](/Users/chinonsoude/Desktop/Projects/dreamsAi/store/index.ts:4)
keeps its URI only in memory. There is no persisted draft, upload queue, or persisted
journal cache.

Closing the app, losing connectivity, or failing AI processing can interrupt the
capture flow without a recoverable saved entry. The error screen from the editor
has no retry action.

Save a local draft immediately, preserve original text and audio in durable app
storage, and sync independently. Give users a visible status: Saved on this device,
Syncing, Synced, or Needs attention. Run optional analysis after the original entry
is saved. Users should be able to keep a dream without paying or waiting for AI.

### 4. High: recordings can become attached to the wrong dream

The recording URI is set after capture but never cleared. The
[summary save mutation](/Users/chinonsoude/Desktop/Projects/dreamsAi/app/summary/index.tsx:95)
uploads whatever URI is still in the global store, including when the screen displays
a newly typed dream from its `dreamData` parameter.

Source-derived reproduction: record and save dream A, then type dream B in the same
session. The summary displays B, but saving B can upload and attach A's recording.

Use an explicit draft object with its own ID and input type. Associate audio with
that draft, clear completed/discarded drafts, and never infer the current entry's
audio from a global leftover URI. Test switching from voice to text and between
multiple drafts.

### 5. High: failed audio processing or upload can look successful

[Transcription](/Users/chinonsoude/Desktop/Projects/dreamsAi/util/transcribeAudio.ts:23)
returns the literal text "Failed to transcribe audio" on failure. Downstream code
treats it as a real dream transcript. The
[upload helper](/Users/chinonsoude/Desktop/Projects/dreamsAi/app/summary/index.tsx:73)
returns `null` on failure, and the save mutation can still insert the dream and show
a success message without its recording.

Transcription failures should produce an error state while preserving the original
recording. Separate text-save success from audio-upload success. Provide Retry
transcription, Retry upload, and Keep audio without analysis. Bound timeouts and
retries, validate the returned data, and record each processing stage's status.

Analysis/transcription currently run in a React Query query whose key includes
subscription state. A changed entitlement, remount, or reconnect can re-run expensive
processing. Use an explicit mutation or durable server job with a stable request ID.

### 6. High: reminders contradict the user's settings

[Startup](/Users/chinonsoude/Desktop/Projects/dreamsAi/contexts/ContextWrappers.tsx:40)
always calls [InitialiseNotifications](/Users/chinonsoude/Desktop/Projects/dreamsAi/util/notification.ts:6).
It requests permission, clears every scheduled notification, and schedules five
notifications every two days at 5 AM without reading the saved preferences. The first
date can already be in the past. Settings separately offers a daily 8 AM reminder.

Turning reminders off can be undone by reopening the app. Startup can also replace
the daily schedule with a different one.

Use one scheduler based on saved preferences, an optional chosen wake-up time and
days, and stable notification identifiers. Respect opt-outs on restart and system
permission changes. Ask for permission when the user enables reminders. Cancel only
the reminders owned by this feature. Avoid reminder notifications on days the user
has already recorded if that behavior is part of the product promise.

### 7. High: the journal has no account recovery path

The app automatically uses anonymous Supabase sign-in. Account actions are commented
out in [Settings](/Users/chinonsoude/Desktop/Projects/dreamsAi/app/(tabs)/settings.tsx:176).
There is no login, account linking, export, or account deletion flow. Anonymous access
is convenient initially, but it is inadequate as the only identity for a long-lived
personal journal.

Keep guest entry easy, then offer "Protect your journal" with Apple, Google, or email
linking. Preserve the guest's entries when linking, support existing-account conflicts,
and connect the same identity to purchases. Add export and account/data deletion.
Scope cached queries by user and clear private cached data on account transitions.

[Supabase anonymous sign-ins](https://supabase.com/docs/guides/auth/auth-anonymous)
documents the loss of account access after signing out, clearing local data, or moving
to another device unless an identity is linked. The local config also disables
anonymous sign-ins; that is a local configuration mismatch, not proof of the live setting.

### 8. High: privacy promises need verified backend enforcement

The client builds public audio URLs in
[summary upload](/Users/chinonsoude/Desktop/Projects/dreamsAi/app/summary/index.tsx:78).
If the bucket is public, someone with a URL can retrieve the recording. If it is
private, playback needs an authenticated download or signed URL. The bucket's actual
visibility could not be verified.

Use a private bucket, store object paths, and issue short-lived signed URLs or
authenticated downloads. Verify ownership policies for every dream operation and
storage operation. Client-side `user_id` filters are not a replacement for database
authorization. Establish explicit consent for sending dream content to AI providers,
clear retention controls, and private notification previews. A biometric lock would
also be useful for this category, alongside secure storage of session credentials.

[Supabase bucket visibility](https://supabase.com/docs/guides/storage/buckets/fundamentals)
and [storage access controls](https://supabase.com/docs/guides/storage/security/access-control)
explain these distinctions. Do not claim end-to-end encryption without implementing
and validating its implications for sync and server-side AI.

## Functionality that would make the journal useful

| Improvement | Current gap | Useful behavior |
| --- | --- | --- |
| Fast capture | Text entry, paywall, processing, summary, and final save precede a completed entry | Open directly into text or recording, autosave, and show an immediate saved state |
| Search and filters | Home retrieves the whole list with no search, ordering, pagination, or filters | Search text/title; filter by date, mood, tag, recording, and favorites; newest-first pagination |
| Calendar and timeline | Onboarding promises a timeline; Home is a masonry grid | Browse dreams by the night they occurred; switch between calendar and chronological list |
| Useful detail view | Saved details show transcript/keywords/audio but omit the saved AI summary and mood | Show original account, summary, user mood, reflection, and related dreams together |
| Favorites | Starring exists in the action menu, but Home has no favorites filter or visible star indicator | Make stars visible and offer a favorites collection |
| Better recording | Pause changes the central control back to a microphone; there is no distinct finish-from-paused action | Explicit Record, Pause, Resume, Finish, and Discard; playback and transcript correction before analysis |
| Better playback | The displayed seeker is decorative; errors hide the player | Real seeking, speed controls, loading/error states, and retry |
| Custom reminders | Fixed conflicting schedules | Choose wake-up time and days, respect time-zone changes and opt-outs |
| Export and recovery | No portable journal or recoverable identity | Export selected/all entries as text or PDF and structured data; link a permanent account |
| Recurring themes | AI analyzes one dream at a time; no aggregation UI | Weekly theme/mood summaries with links to the entries behind each observation |
| Related dreams | No historical context in the AI request | Show entries with similar themes and offer optional comparisons grounded in those entries |
| Personal reflection | AI formats and summarizes; onboarding also advertises interpretation | Optional reflection questions and possible associations, clearly separated from the original dream and the user's own meaning |

Start recurring insights with transparent tag counts, user-recorded moods, and linked
entries. Add semantic matching when enough entries exist to make it useful. Preserve
the original text and transcription: AI formatting or interpretation must not replace
the only copy of what the user recorded. Let users correct tags and mood classifications.

Recommended primary navigation: **Journal / Capture / Insights**, with Settings or
Account accessed from the journal header. The current "Profile" tab only contains
settings. A single prominent capture action should be easy to reach when waking up.

## Additional implementation issues

- **Date consistency:** the editor sends `dream_date`, but it is absent from the local
  Journal type. Cards and detail screens display `created_at`, so backdated dreams
  appear under their creation date. Use a defined dream date separately from capture
  and sync timestamps, and reconcile it with the actual database schema. Supabase
  auth IDs are UUID strings, while the local type declares `user_id` as a number and
  some paths call `parseInt` on it. The final insert overrides that field with the
  actual user ID, so those conversions are not by themselves proof that inserts fail.
- **Incomplete states:** the detail screen checks `error && isLoading` and otherwise
  renders an empty-looking detail when loading or failing. Summary passes a mutation
  error boolean as an Error object. Add real loading, not-found, retry, and recoverable
  save states. Disable repeated save/update/delete actions while pending.
- **Deletion consistency:** detail deletes storage first, then the database row;
  either stage can fail independently. Use a recoverable delete workflow with tracked
  cleanup, and consider Trash/Undo before permanent removal.
- **Stale menu actions:** the global action-menu callback only refreshes when star
  state changes. Editing a title or transcript can leave Share using older content.
  Configure the screen header from its current state and remove the global callback.
- **Navigation and Android polish:** the fallback icon map lacks `plus` and
  `person.fill`, both used by the tab bar. Active-tab matching compares normalized
  pathnames with route-group paths. The absolute tab bar has a fixed bottom offset,
  and the journal list does not reserve its height. Use navigation state, safe-area
  insets, and bottom content padding. The recorder uses iOS-only FullWindowOverlay
  on every platform; gate it by platform. Replace the old native SafeAreaView with
  the safe-area-context component and verify edge-to-edge Android screens.
- **Accessibility:** the onboarding completion control uses `onTouchStart` on a
  BlurView rather than a semantic pressable button. Add roles, labels, selected states,
  adequate targets, and scalable text. Permission switches currently request access
  regardless of whether the user is toggling on or off; use clear grant/status/settings
  controls instead.
- **Startup resilience:** AuthProvider does not unsubscribe its listener or handle
  session-fetch rejection. Signup ignores the error and uses the pre-signup user when
  assigning analytics identity. Fonts have no explicit error fallback. Centralize
  startup/auth status and provide recoverable failures.
- **Analytics accuracy:** "Dream Added" fires before processing succeeds and "Dream
  Saved" before persistence succeeds. Record successful local save, sync, analysis,
  purchase, and entitlement unlock separately. Never include dream text in analytics.
- **Onboarding:** five screens, upfront permissions, a rating request, and a paywall
  precede a user's first saved dream. Shorten this to a clear promise and immediate
  capture. Request a rating after demonstrated use. Align every promise with a feature
  users can access.

## Suggested implementation sequence

### Release 1: trustworthy capture and paid access

1. Move AI behind an authenticated server endpoint and rotate exposed credentials.
2. Fix entitlement state, same-action unlocking, platform keys, and purchase restore.
3. Introduce persisted drafts with entry-specific audio and reliable local saving.
4. Add recoverable transcription/upload states and server-enforced limits.
5. Unify reminder scheduling and respect saved preferences.
6. Verify live ownership/storage policies and establish private audio access.

Acceptance: an offline or interrupted entry is recoverable; a newly purchased user
can immediately access the intended action; a written entry cannot inherit another
entry's audio; failed transcription cannot become journal content; disabled reminders
stay disabled after restart.

### Release 2: a complete everyday journal

Add account linking/recovery, searchable chronological browsing, favorites, date and
mood filters, calendar navigation, editing before analysis, actionable Settings,
export, privacy controls, and accessible navigation. Resolve the small UI defects
and simplify onboarding around saving the first entry.

Acceptance: users can find an old dream, preserve it across devices, export it, correct
its transcript/date/mood, and recover from a save or playback failure.

### Release 3: useful insights from a growing history

Add weekly reviews, recurring themes, related dreams, and optional reflection based
on the user's actual entries. Link each observation to its evidence. Treat personal
interpretations as suggestions and let the user provide the meaning and context.

Suggested commercial structure: make basic capture, saving, retrieval, and ownership
dependable for everyone; test a limited AI preview, then offer premium analysis,
historical comparisons, and weekly insights. Entitlement and quota enforcement belongs
on the backend. Pricing and conversion impact require actual usage evidence.

## How to judge whether changes help

Track first successful saved dream, time from opening capture to a local save, entry
and audio-sync failure rates, completed analyses, repeat journaling over seven and
28 days, reminder opens leading to saved entries, and purchase-to-unlock failures.
Track backend AI requests/cost by job, without logging dream content.

Expand verification around interrupted/offline capture, voice-to-text transitions,
purchase/restore/cancel, permission denial, account linking, cross-account cache
isolation, reminder preference persistence, and database/storage ownership. Add
physical-device checks for microphone interruptions, audio playback, large text,
screen readers, safe areas, and Android purchase configuration.
